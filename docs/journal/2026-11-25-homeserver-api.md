## 1. 센서 API: 펌웨어의 3초를 지키는 법 (SCRUM-239)

- 사용자: "239 티켓 워크플로우로 진행해줘"
- 계약은 앞 노트 10절 그대로다.

```
GET http://<홈서버>/api/thermostat/sensors

{
  "sensors": [
    { "id": "livingroom", "name": "거실",
      "temperature": 21.4, "updated_at": "2026-11-24T21:15:00+09:00" }
  ]
}
```

### 1.1 API는 SmartThings를 부르지 않는다

- 펌웨어는 1분마다 부르고 **3초**만 기다린다. 요청이 올 때마다 홈서버가 SmartThings 클라우드에 센서 수만큼 물어보면, 클라우드가 조금만 느려도 3초를 넘긴다.
- 결정: 홈서버 안의 백그라운드 스레드가 60초마다 센서를 읽어 **마지막 값을 들고 있고**, API는 그 값을 바로 돌려준다.
- 한 센서 조회가 실패하면 그 센서의 **이전 값을 그대로 둔다.** `updated_at`이 홈서버가 읽은 시각이 아니라 센서가 SmartThings에 마지막으로 보고한 시각이라, 오래된 값은 펌웨어가 10분 기준으로 알아서 거른다. 판단은 펌웨어에 두고, 홈서버는 사실만 전한다.
- 한 번도 값을 얻지 못한 센서는 목록에 넣지 않는다.

> 웹 개발자 시선: 요청 경로에서 외부 API를 부르지 않고 캐시를 내주는 구조다. "stale-while-revalidate"를 서버 쪽에서 직접 한 셈이다. 캐시 값이 얼마나 낡았는지는 응답에 `updated_at`으로 실어 보내고, 버릴지는 클라이언트가 정한다.

### 1.2 펌웨어 파서가 정한 홈서버 규칙

- 홈서버 계획을 쓰기 전에 펌웨어 쪽 파서(`src/sensor/sensor_logic.cpp`, SCRUM-235·236에서 이미 만든 것)를 읽었다. 거기서 계약 문서에 없던 규칙 두 개가 나왔다.
  1. `updated_at`에 `null`이 오면 **응답 전체**를 못 읽는다. 그래서 시각이 없는 센서는 `null`로 보내지 않고 목록에서 뺀다.
  2. `updated_at`에는 반드시 오프셋(`Z` 또는 `+09:00`)이 있어야 한다. SmartThings가 주는 UTC 시각을 서울 시각(`+09:00`)으로 바꿔 초 단위로 내보낸다.
- 그 밖에 정한 것:
  - 화씨(`F`) 센서는 섭씨로 바꾸고 소수 둘째 자리에서 자른다. 숫자가 아니거나 무한대면 값이 없는 것으로 본다.
  - API 키는 선택이다(로컬 네트워크 전용). 키를 정해 두면 `X-API-Key` 헤더가 같아야 하고, 다르면 401이다. 비교는 시간 차로 키를 알아낼 수 없는 방식(`hmac.compare_digest`)으로 한다.
  - 센서 설정이 비었으면 503 `{"error": "온도조절기 센서가 설정되지 않았습니다"}`.
  - 가짜 모드(`DASHBOARD_FAKE`)에서는 고정 JSON 파일을 내준다. 펌웨어를 개발할 때 SmartThings 없이 쓰기 위해서다.
- 설정은 홈서버 `.env`에 `THERMOSTAT_SENSORS=<id>=<SmartThings 기기 ID>=<이름>,...` 한 줄이다.

> 교훈: 계약 문서는 "무엇을 보낸다"까지만 적는다. "무엇을 보내면 안 된다"는 받는 쪽 파서 코드에 있다. 서버를 만들기 전에 클라이언트 파서부터 읽는다.

### 1.3 실제 응답은 받지 못했다

- 실제 데이터를 해석하는 작업이라, 맡기기 전에 실제 SmartThings 응답을 받아 표본으로 넣으려 했다.
- 이 PC에 있던 SmartThings OAuth 토큰이 만료돼 있었다(`invalid_grant`). 다시 인증하지 않았다. 홈서버가 24시간마다 같은 토큰을 갱신하고 있어서, 노트북에서 새로 인증하면 홈서버의 갱신 토큰이 무효가 될 수 있다.
- 홈서버 세션에 물어보려 했지만 홈서버 쪽 원격 실행 환경에도 닿지 않았다.
- 결정: SmartThings 공개 문서의 상태 응답 모양(`temperatureMeasurement.temperature`의 `value`, `unit`, `timestamp`)으로 표본을 만들고, 계획에 "실제 값은 머지 뒤 홈서버에서 확인"이라고 적었다(`문헌 기반`).

> 책 소재: 토큰은 홈서버가 들고 있다(앞 노트 책 구성 8장). 그래서 노트북에서는 실제 센서 값을 볼 수 없었다. 운영 서버만 가진 자격증명으로 운영 데이터를 확인하는 문제는 웹 개발자에게도 익숙하다. 개발 PC에서 운영 토큰을 새로 발급하면 운영 쪽이 끊길 수 있다.

## 2. 시각 API: NTP가 안 될 때 (SCRUM-252)

- 센서 API를 진행하는 동안 사용자: "그리고 시간 갱신용 api도 하나 만들까? 티켓 추가해줘."
- 목적: 펌웨어는 NTP로 시각을 맞추고 보드 RTC로 유지한다(앞 노트 10.2). 공유기가 바깥 NTP 서버에 닿지 못할 때 같은 로컬 네트워크의 홈서버에서 시각을 받으면 된다. 센서의 "N분 전" 표시와 10분 기준 판단이 모두 시계에 기대고 있다.

```
GET http://<홈서버>/api/thermostat/time

{ "now": "2026-11-25T10:00:00+09:00", "epoch": 1795568400 }
```

- 결정:
  - 외부를 부르지 않고 즉시 응답한다.
  - `now`(오프셋이 붙은 서울 시각, 1.2절 규칙과 같다)와 `epoch`(UTC 초)를 **같은 한 시각**에서 만든다. 시각 함수를 두 번 부르면 초 경계에서 둘이 어긋날 수 있다.
  - 센서 설정이 꺼져 있어도 시각 API는 동작한다. API 키 규칙은 센서 API와 같다.
- 실수 하나: 일감 본문에 epoch 예시를 `1764032400`으로 적었다. 이 값은 **2025년** 11월 25일이다. 2026-11-25T01:00:00Z는 `1795568400`이다. 계산하지 않고 그럴듯한 숫자를 적은 것이다. 계획과 일감 댓글에 바로잡은 값을 남겼다.

> 교훈: 시각 예시는 계산해서 적는다. 사람(과 AI)이 쓴 epoch는 1년쯤 틀려도 그럴듯해 보인다. 테스트 표본에는 날짜 경계(12월 31일 15:30 UTC → 서울 1월 1일)처럼 틀리기 쉬운 값을 같이 넣었다.

> 웹 개발자 시선: 사내망의 시간 서버, 또는 헬스체크 응답에 서버 시각을 실어 주는 것과 같다. 시계가 틀린 클라이언트는 캐시 만료와 토큰 만료부터 이상해진다.

## 3. API 목록: 레포 말고 API로 (SCRUM-253)

### 3.1 처음 생각은 문서였다

- 사용자: "그리고 에이전트들이 볼수있게, api에 swagger 같은거도 만들까? 굳이 스웨거일 필요까진 없고, 그냥 어떤 종류의 API가있고 각 API에서는 어떤 정보가 제공된다 정도면 될것 같아."
- Claude가 처음 쓴 일감은 레포 안에 API 목록 문서를 두는 안이었다.
- 사용자: "253은 근데 레포를 봐야 알수있잖아. 나는 그냥 api 호출로 파악하게 하고 싶은데?"
- 맞는 지적이다. 이 API를 쓸 에이전트는 **다른 레포**(이 펌웨어 레포 같은)에서 일한다. 홈서버 레포를 열어 볼 수 없거나, 열면 그만큼 토큰을 쓴다. 그래서 일감을 바꿨다.

### 3.2 목록은 코드에서 만든다

```
GET http://<홈서버>/api

{
  "service": "home-dashboard",
  "apis": [
    { "method": "GET", "path": "/api/thermostat/sensors",
      "summary": "온도조절기용 원격 온도 센서 값",
      "description": "인증: ... 응답: ... 오류: ...",
      "params": [{"name": "X-API-Key", "in": "header", "required": false}] }
  ]
}
```

- 결정:
  - 목록을 손으로 따로 적지 않는다. 각 API 정의에 붙인 한 줄 요약(`summary`)과 설명(`description`: 인증, 응답 필드, 오류 코드)을 서버가 읽어 목록을 만든다. 손으로 적은 목록은 언젠가 실제 API와 어긋난다.
  - `/health`와 `/api`로 시작하는 것만 넣는다. 화면 페이지와 정적 파일은 뺀다. `GET /api` 자신도 들어간다.
  - 인증 없이 연다. 목록만 주고 데이터 값이나 설정값(키, 토큰, 기기 ID)은 주지 않는다.
  - **설명이 빈 API가 하나라도 있으면 깨지는 테스트**를 둔다. 다음에 API를 추가하는 사람(또는 AI)이 설명을 빼먹으면 테스트가 막는다.
  - 설명을 쓰기 전에 각 API의 실제 응답 코드를 읽고 그대로 적게 했다. 추측해서 적은 설명은 없는 것보다 나쁘다.
- 같은 값으로 FastAPI가 기본으로 주는 `/docs`(Swagger 화면)도 쓸 만해졌다. 사용자가 처음 말한 "swagger 같은거"가 덤으로 따라왔다.

> 웹 개발자 시선: OpenAPI와 같은 생각이다. 문서를 코드 옆에 두고 코드에서 뽑으면 둘이 어긋나지 않는다. 여기서 다른 점은 읽는 쪽이 사람보다 **에이전트**라는 것이다. 에이전트에게는 화려한 Swagger 화면보다 JSON 한 번이 낫다.

> 교훈: "누가 읽는가"를 먼저 묻는다. 같은 API 목록이라도 레포 안 문서는 그 레포에서 일하는 사람용이고, `GET /api`는 바깥에서 부르는 쪽용이다.

## 4. 두 일감을 동시에

- 사용자: "252 253 동시진행 가능할까? 가능하면 워크플로우로 돌려줘"
- 둘 다 같은 파일(`thermostat.py`)에 손을 대야 했다. 252는 시각 API를 그 파일에 더하고, 253은 그 파일의 센서 API에 설명을 붙인다.
- 정한 것:
  - **파일 소유권을 나눴다.** 252는 `thermostat.py`의 새 라우트(파일 끝 `return router` 바로 앞), 그 테스트, README. 253은 앱 본체, 관리 API, 새 목록 모듈, 에이전트 안내 문서, 그리고 `thermostat.py`에서는 센서 API의 설명 한 줄만.
  - **규칙을 먼저 공유했다.** "새 API에는 한 줄 요약과 한국어 설명(인증, 응답, 오류)을 반드시 단다"는 규칙을 두 계획에 똑같이 적었다. 252는 253이 무엇을 만드는지 몰라도, 이 규칙만 지키면 253의 목록에 들어간다.
- 결과: 252를 먼저 머지하고, 253 브랜치에 최신 main을 합쳤다. **충돌이 없었다.** 합친 뒤 전체 테스트 453개가 통과했다. 3.2절의 "설명 없는 API가 있으면 깨지는 테스트"가 252의 시각 API까지 확인했다.
- 검토: 구현 뒤 검토를 맡는 Qwen이 세 일감 모두 예산 한도 초과(HTTP 429)로 돌지 못했다. Claude가 각 계획의 "검토할 점(Review Focus)" 범위만 직접 봤다. 253은 API 설명에 적힌 필드와 오류 코드를 실제 코드와 하나씩 맞춰 봤다.

| 일감 | 내용 | PR | 구현 비용(DeepSeek) |
|---|---|---|---|
| SCRUM-239 | 센서 API `GET /api/thermostat/sensors` | #28 머지 | $0.08 |
| SCRUM-252 | 시각 API `GET /api/thermostat/time` | #29 머지 | $0.02 |
| SCRUM-253 | API 목록 `GET /api` | #30 머지 | $0.06 |

> 책 소재: 앞 노트 14.2절의 "줄 세우기에서 동시에 달리기로"가 이번엔 파일 한 개 안에서 일어났다. 일감 그래프에 화살표가 없어도 같은 파일을 만지면 부딪힌다. 화살표 대신 "누가 어느 줄을 가진다"를 정했다.

> 웹 개발자 시선: 모노레포에서 CODEOWNERS로 소유권을 나누고, 린트 규칙으로 컨벤션을 강제하는 것과 같다. 소유권은 충돌을 막고, 테스트로 강제한 규칙은 서로 몰라도 맞물리게 한다.

> 교훈: 두 작업이 서로를 기다리지 않게 하려면 **인터페이스가 아니라 규칙**을 공유해도 된다. "설명을 단다"는 규칙 하나로 252와 253은 서로의 코드를 보지 않고 맞물렸다.

## 5. 아직 안 한 것

- **홈서버에 반영하지 않았다.** 홈서버에서 pull과 서비스 재시작, `.env`에 `THERMOSTAT_SENSORS` 추가가 필요하다. 서버 상태를 바꾸는 일이라 사용자가 시킬 때 한다.
- 그 뒤 `GET /api`, `/api/thermostat/sensors`, `/api/thermostat/time`의 실제 응답을 확인한다. 이것으로 SCRUM-239 완료 기준의 "실제 센서 값 확인"이 끝나고, 1.3절의 `문헌 기반` 표본이 `실측`이 된다.
- 펌웨어 쪽: NTP가 실패하면 시각 API로 시계를 맞추는 흐름을 펌웨어 통합(SCRUM-242)에 넣는다.
- Qwen 검토 예산을 충전해야 다음 일감부터 검토가 다시 돈다.
