## 1. "온도랑 시간을 서버에서 싱크해 오는거잖아?"

- 절반만 맞다.
  - **온도:** 1분마다 `<홈서버>/api/thermostat/sensors`에서 거실 센서 값을 받는다. 보드 센서(SHT40)가 아직 없어서 지금은 유일한 온도이고, 이 값이 Matter를 거쳐 SmartThings 앱의 현재 온도로도 올라간다.

## 2. "목표온도를 올렸는데도 대기중으로 보여"

- 사용자: "가상이긴 하지만, 목표온도를 올렸는데도 대기중으로 보여."
- "가상"은 스마트 플러그·구동기가 아직 연결되지 않았다는 뜻이다. 펌웨어가 판단한 "난방 중/대기"만 화면과 SmartThings에 보인다.

### 2.1 증거 (`실측`)

시리얼 `status`를 1분 간격으로 두 번 읽었다.

| 시각 | 목표 | 현재 | `heating` |
|---|---|---|---|
| 0초 | 25.00℃ | 21.00℃ | 0 |
| 59초 | 25.00℃ | 21.00℃ | **1** |

- 켜짐 기준은 목표 − 0.5℃ = 24.5℃이고 현재는 21℃다. 판단이 틀릴 수가 없다.
- 제어 판단(`step`)은 1초마다 돈다. 그런데도 1분 가까이 대기였다면, 코드상 남는 경로는 **최소 꺼짐 시간(5분)** 하나다. 구동기가 느려서 짧게 깜빡이지 않도록 "꺼진 뒤 5분 안에는 다시 켜지 않는다"는 규칙이다(CLAUDE.md 7절).
- 그 대기 이유(`kMinOffHold`)는 컨트롤러 안에만 있고 화면에도 `status`에도 나오지 않는다. 겉으로는 "난방이 필요 없음"과 구별이 안 된다.

### 2.2 5분이 걸리는 두 경우

1. 5분 안에 난방이 꺼진 적이 있을 때(예: 목표를 내렸다가 다시 올림).
2. **재부팅 직후.** 부팅 때 첫 홈서버 조회가 실패하면(이날 로그에도 `home server fetch failed`, `실측`) 첫 판단은 "온도 없음 → 끔"이 되고 그 시각부터 5분을 센다. 온도가 들어와도 부팅 후 5분이 지나야 켜진다.

- 2번을 재현하려고 재부팅 후 상태를 계속 읽었지만, 재부팅에서 USB 시리얼이 끊기고 다시 연결한 뒤 응답이 오지 않아 데이터를 얻지 못했다. 사용자가 처음 본 상황이 1번인지 2번인지는 확인하지 못했다(`확인 필요`).
- 사용자: "결국 원인은 뭐였던거야?" → 최소 꺼짐 시간 대기. 고장은 아니고, 이유가 안 보여서 헷갈린 것.

### 2.3 사용자의 결정

- 사용자: "너무 잦은 온오프는 좋지는 않아서 일반적으로는 5분간격 괜찮은거 같아. / 다만 온도 변경, 반복 설정 변경 직후에는 저 타이머가 적용되지 않아야 할것 같아."
- 규칙의 목적(구동기 보호)은 지키고, 사람이 일부러 바꾼 순간만 예외로 둔다는 뜻이다.

> 웹 개발자 시선: 입력을 디바운스하되, 사용자가 "저장" 버튼을 누른 순간에는 디바운스를 건너뛰고 바로 반영하는 것과 같다.

### 2.4 구현 (SCRUM-335, PR #16)

- 구현 주체: Claude(core 컨트롤러 10줄 남짓, 난방 제어 경로).
- `ZoneController::set_config`가 새 설정의 **모드·목표온도·반복 N분** 중 하나라도 이전과 다르면 플래그를 세운다. 다음 `step` 한 번은 최소 켜짐/꺼짐 시간을 적용하지 않고, 플래그는 그 자리에서 지운다(전환이 없어도 한 번에 소모).
- 같은 값을 다시 넣는 경우(NVS 복원, Matter 되돌림)는 변경으로 보지 않는다.
- Claude가 정한 것: 모드 변경도 포함(꺼짐→온도 모드도 사용자가 바꾼 것), 목표를 **내릴** 때(최소 켜짐 시간)도 건너뜀("타이머가 적용되지 않아야"를 양방향으로 해석).
- 최저온도 보호, 센서 이상 즉시 정지, 유지 신호는 그대로.
- 테스트부터 썼다. 새 테스트 6개 중 4개가 먼저 실패하는 것을 보고 구현했다(목표 올림·내림, 한 번만 적용, 같은 값, 모드 변경, 반복 N분 변경). Qwen 검토는 지적 0건.

### 3.1 다시 보니 헤더 탓이 아니었다

먼저 지난 빌드의 흔적(파일 시각)을 봤다(`실측`).

| 시각 | 일 |
|---|---|
| 08:28 | 빌드 시작(`build.options.json` 기록) |
| 08:56 | `includes.cache`, `libraries.cache` 기록 → **감지 단계 28분** |
| 08:58~09:16 | WiFi·Network·LVGL·Matter·우리 라이브러리 오브젝트 새로 생성 → **약 20분** |
| 09:19 | 링크 끝 |

Arduino 코어 오브젝트(`core/`)는 이틀 전 것 그대로였다. 라이브러리만 전부 다시 만든 것이다.

### 3.2 arduino-cli가 캐시를 버리는 조건 (`문헌 기반`, v1.6.0 소스)

- **`includes.cache`는 순서 있는 목록이다.** 파일마다 "이 파일을 전처리했더니 이 헤더가 없더라"를 차례로 적어 둔다. 다음 빌드는 앞에서부터 맞춰 보다가 **한 항목이라도 어긋나면 그 뒤를 전부 잘라 버린다.** 잘린 뒤의 파일은 모두 다시 전처리하고, 병렬로 미리 돌리던 전처리기(pre-runner)도 취소한다. 그래서 감지가 직렬로 느려진다.
- **`libraries.cache`(include 폴더 목록)가 한 글자라도 다르면** "The list of included libraries has been changed... rebuilding all libraries"를 내고 라이브러리 빌드 폴더의 오브젝트를 모두 지운다.
- **`build.options.json`(스케치·라이브러리 경로, 빌드 속성)이 다르면** 빌드 폴더를 지운다.
- **오브젝트를 다시 쓸지는 mtime으로만 정한다**(`ObjFileIsUpToDate`). 소스나 `.d`에 적힌 헤더가 `.o`보다 새로우면 다시 컴파일한다. 컴파일 명령이 같은지는 보지 않는다.

### 3.3 재현 실험 (`실측`)

오브젝트는 만들지 않고 감지까지만 하는 `--only-compilation-database`로 쟀다.

| 실험 | 감지 시간 | 캐시 | 라이브러리 재컴파일 |
|---|---|---|---|
| 바꾼 것 없음 | 48초 | 365개 파일 모두 사용 | — |
| `src/core/thermostat_controller.h` 시각만 바꿈 | 190초 | `thermostat_firmware.cpp` 하나만 다시 감지(전처리 16개 병렬), 나머지 사용 | 없음 |

헤더 변경은 2~3분을 더할 뿐이었다. 그럼 50분은?

- 지난 명령 기록을 뒤져 보니, 메인 체크아웃의 `.build`를 마지막으로 빌드한 건 11-27 오후의 **계측용 빌드**였다. 그때는 아직 두꺼운 스케치였고 `src/firmware` 라이브러리도 없었다.
- 얇은 스케치로 바뀐 뒤 **이 폴더에서 처음 한 빌드**가 바로 08:28 빌드였다. 라이브러리 목록 세 번째 자리에 `src/firmware`가 끼어들었으니 `includes.cache`는 거의 맨 앞에서 어긋났고(감지 28분), `libraries.cache`도 달라져 라이브러리를 모두 지웠다(20분).
- 새 워크트리 첫 빌드 55분도 같은 구조다. 캐시가 아예 없으니 감지를 직렬로 하고 라이브러리를 전부 컴파일한다.
- 일감에 남긴 "헤더 변경" 댓글을 정정했다.

> 교훈: "마지막으로 바꾼 것"이 원인이라는 추정은 쉽게 틀린다. 그 빌드 직전에 무엇이 이 폴더를 만졌는지(빌드 폴더의 이력)를 먼저 봐야 했다.

## 4. 경로를 고정한다 (SCRUM-333)

### 4.1 두 갈래를 시험

| 방법 | 실험 | 결과 |
|---|---|---|
| 감지 건너뛰기(`--skip-libraries-discovery`, 도움말에 없는 옵션) | 감지만 / 전체 빌드 | 감지 19초로 줄었지만 **링크 실패**(`ld returned 1`). 이 모드에선 라이브러리 목록이 비어 라이브러리가 링크되지 않는다. 버림 |
| 고정 경로(`subst T: <워크트리>`) | `T:\` 경로로 빌드 시작 후 `build.options.json` 확인 | `"sketchLocation": "T:\\firmware\\thermostat_main"`. arduino-cli가 가상 드라이브를 실제 경로로 바꾸지 않는다. 채택 |

> 웹 개발자 시선: 캐시 키에 절대 경로가 들어가서 체크아웃 위치만 달라도 캐시가 다 깨지는 CI와 같다. Docker 빌드에서 항상 `/app`에 소스를 두는 것처럼, 어디서 빌드하든 같은 경로로 보이게 만든다.

### 4.2 설계

1. compile할 때만 `subst T: <워크트리>`로 연결하고, compile 명령의 경로(스케치, `--library`, `-I`, `--build-path`)를 `T:\` 기준으로 바꾼다. 빌드 폴더의 실제 위치는 워크트리 안 그대로다. 끝나면 실패·예외에도 연결을 푼다. upload는 실제 경로를 쓴다.
2. `T:`는 사용자 세션 전체에 하나라서, compile 동안 **잠금 파일**을 잡는다. 다른 빌드가 잡고 있으면 기다린다. 프로세스가 죽으면 OS가 잠금을 풀어 준다(Windows `msvcrt.locking`, POSIX `fcntl.flock`).
3. 새 워크트리는 메인 체크아웃의 빌드 폴더를 **복사해서 시작**한다(메인이 고정 경로로 빌드돼 있을 때만).
4. 복사한 뒤 **우리 소스로 만든 오브젝트는 지운다**(`sketch/`, `modules.txt`의 라이브러리 폴더, `.ino.*` 산출물). 서드파티 라이브러리와 코어 오브젝트만 남긴다.

4번이 이 설계에서 가장 중요한 한 줄이다. arduino-cli는 mtime만 보므로, 메인에서 10:31에 빌드한 오브젝트를 10:00에 체크아웃한 워크트리로 가져오면, 워크트리에서 **내용이 다른** 파일도 "소스가 더 오래됐다"며 메인의 오브젝트를 그대로 쓴다. 에러 없이 **다른 코드로 만든 펌웨어**가 나온다. 우리 소스 오브젝트를 지우면 그 파일들은 반드시 다시 컴파일된다.

- 드라이브 글자가 이미 실제 드라이브로 쓰이고 있으면 건드리지 않고 지금 방식으로 빌드한다. `--dry-run`은 연결·잠금·복사 없이 명령만 출력한다.
- 구현 주체: DeepSeek(빌드 도구만 바꾸는 일, 계획에 함수·테스트를 정함). Qwen 검토 1회 통과(PR #17, $0.098). 실제 빌드 측정은 DeepSeek 워크트리에서 할 수 없어 Claude가 직접 했다.

- 메인과 새 워크트리에서 만든 바이너리는 **64바이트만 달랐다.** 앱 설명 안의 ELF SHA-256(32바이트)과 이미지 끝의 SHA-256(32바이트)이다. 실행되는 코드와 데이터는 같고, ELF가 다른 건 디버그 정보 차이로 본다(`추정`). 새 워크트리 두 개끼리도 65바이트가 달랐다(같은 종류로 보지만 바이트별로 확인하지는 않음).

## 알게 된 점

- 안전 타이머는 목적(구동기 보호)을 지키는 선에서, 사람이 일부러 바꾼 순간은 예외로 둘 수 있다. 다만 **대기 이유가 화면에 보이지 않으면** 사용자는 고장으로 본다.
- arduino-cli의 감지 캐시는 순서 있는 목록이라, 앞에서 한 번 어긋나면 뒤를 모두 버리고 직렬로 다시 한다. 라이브러리 목록이 바뀌면 라이브러리를 전부 다시 컴파일한다.
- 빌드 캐시가 mtime만 볼 때는, 다른 소스 트리의 오브젝트를 가져오는 순간 "에러 없는 잘못된 빌드"가 생길 수 있다. 가져온 쪽의 우리 소스 오브젝트는 지우고 시작한다.
- 숨은 옵션(`--skip-libraries-discovery`)은 이름만 보고 쓰면 안 된다. 감지는 빨라졌지만 링크가 깨졌다.

## 오늘 정한 것
