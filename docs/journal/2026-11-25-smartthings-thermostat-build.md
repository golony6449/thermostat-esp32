## 1. 격리된 빌드 환경과 호스트 테스트 뼈대 (`SCRUM-232`)

- **결정:** `C:\Users\seongheum\AppData\Local\thermostat-esp32\arduino-cli.yaml`로 프로젝트 전용 격리 설정을 만들고, 그 안에만 `esp32:esp32@3.3.12`를 설치했다. Waveshare 4.3B 오프라인 라이브러리(`ESP32_Display_Panel 1.0.0`, `LVGL 8.4.0` 등)는 기존 sketchbook을 공유했다.
- 제어 로직을 보드 없이 PC에서 단위 테스트할 C++ 컴파일러가 없어 `winget`으로 WinLibs MinGW-w64(`g++ 16.2.0`)를 설치했다.
  - 사용자: "방금 msdn 어쩌구 설치했어?"
  - 답: Microsoft가 아니라 PC용 오픈소스 C++ 컴파일러(MinGW-w64 `g++`)다. ESP32에 매번 굽지 않고 PC에서 `core/` 제어 로직을 1초 만에 테스트하기 위해 설치했다.
- `demos/00_smoke`를 `COM9` 보드에 올려 첫 부팅을 확인했다(`실측`):
  - `core=0.1.0 flash_mb=16 psram_bytes=8388608`
  - FQBN: `esp32:esp32:esp32s3:CDCOnBoot=cdc,USBMode=hwcdc,FlashSize=16M,PSRAM=opi,PartitionScheme=app3M_fat9M_16MB` (`CDCOnBoot=cdc` 필수 — Waveshare 4.3B의 UART0은 RS485에 연결되어 있다).

> 질문 노트 후보: "방금 msdn 어쩌구 설치했어?" → 보드용 크로스 컴파일러(`xtensa-esp32s3-elf-g++`)와 별개로, 순수 C++ 로직을 내 PC에서 바로 돌려 보는 호스트 컴파일러(`g++`)가 필요하다.

> 웹 개발자 시선: 전역 `Arduino15`를 건드리지 않고 프로젝트별 `arduino-cli.yaml`을 둔 것은 Python의 `venv`나 Node의 `nvm`과 같다. 그리고 `core/`를 PC에서 `g++`로 테스트하는 건 브라우저를 띄우지 않고 Node에서 도메인 로직 단위 테스트를 돌리는 것과 같다.

## 5. "NVS가 뭐야?" — 전원을 뽑아도 설정이 남는 법 (`SCRUM-238`)

UI 다음으로 설정 저장 데모(`demos/04_storage`)를 올리려는데 사용자가 물었다.

- 사용자: "NVS가 뭐야?"
- 설명: **Non-Volatile Storage(비휘발성 저장소)**. ESP32 플래시 메모리의 전용 영역에 Key-Value 형태로 데이터를 저장해 전원이 꺼졌다 켜져도 목표온도·모드·반복 시간 같은 설정이 유지되게 한다.
  - 웹의 `localStorage`와 비슷하지만 플래시는 쓰기 횟수 수명이 있어, 버튼을 연타할 때마다 바로 쓰지 않고 **5초 기다렸다가 한 번에 저장(디바운스) + 최소 30초 쿨다운 + 같은 값이면 쓰기 생략**하는 `DeferredWriteGuard`를 뒀다.
  - 또 펌웨어가 바뀌거나 저장 데이터가 깨져도 폭주하지 않도록 헤더에 매직(`THST`)·스키마 버전·IEEE CRC-32 체크섬을 넣어, 깨졌으면 안전 기본값(`꺼짐, 21.0℃, 최저온도 10.0℃`)으로 부팅한다.
- `COM9` 실기 시리얼 검증(`실측`):
  1. 초기 부팅(빈 NVS): `load status=kEmptyOrShort` → 기본값(`21.00℃ / off / repeat 15분`) 적용
  2. `set 24.5 repeat 25` → 5초 후 자동 `[04_storage] NVS flushed` → `reboot` (`RTC_SW_CPU_RST`) → **`load status=kOk`, `target=24.50C mode=repeat repeat_min=25` 복원 확인**
  3. `set 22.0 temp 10` → `flush`(`saved immediately`) → `reboot` → **`kOk`, `22.00C / temp / 10분` 복원 확인**
  4. `erase` → 기본값 초기화 확인

> 질문 노트 후보: "NVS가 뭐야?" → ESP32의 `localStorage`. 단, 플래시 수명 때문에 디바운스를 걸어 쓰기 횟수를 아낀다.

> 웹 개발자 시선: `localStorage.setItem()`에 5초 디바운스 + JSON 스키마 버전 + 체크섬을 붙인 구조. 임베디드에서는 "저장 실패 = 벽돌 또는 오작동"이라 깨진 데이터를 무조건 안전 기본값으로 되돌리는 방어 코드가 필수다.

## 6. 가장 큰 위험을 돌파하다: SmartThings에 직접 만든 Matter 온도조절기 붙이기 (`SCRUM-233`)

2026-11-24 설계에서 가장 큰 미지수이자 위험 1순위였던 검증이었다. *"SmartThings가 DIY Matter 온도조절기를 온도 센서로만 잡지는 않을까? 루틴 조건으로 작동 상태(`ThermostatRunningState`)와 '70분 유지'를 쓸 수 있을까?"*

`demos/01_matter`를 `COM9`에 올렸다(Flash 54%, RAM 32%, `running_state_supported=yes`, `aux_contact=yes`, `CONFIG_ENABLE_CHIPOBLE=y`).

### 6.1 첫 번째 실패: "네트워크를 찾을수 없다는데?"

- 수동 페어링 코드(`3497-011-2332`)를 입력한 사용자: "네트워크를 찾을수 없다는데?"
- 시리얼 로그를 열어 보니 의외의 사실이 찍혀 있었다:
  ```text
  E (249390) chip[SVR]: Failsafe timer expired
  E (249390) chip[SVR]: Commissioning failed (attempt 1): 32
  ```
- **BLE 연결까지는 실제로 성공**했고, 그다음 보드가 Wi-Fi에 붙는 단계에서 실패한 것이었다!
- 원인 둘:
  1. **ESP32-S3는 2.4GHz Wi-Fi만 지원**한다. 스마트폰이 5GHz Wi-Fi에 연결된 상태면 앱이 5GHz SSID를 보드에 넘겨 보드가 네트워크를 찾지 못한다.
  2. Matter 규격상 **11자리 수동 페어링 코드**에는 BLE 디스커버리 플래그(Rendezvous Flag)가 빠질 수 있는 반면, **QR 코드(`MT:Y.K90GSY00KA0648G00`)**에는 `kBLE | kOnNetwork` 플래그가 명시된다.
- 보드를 `decommission`으로 깔끔하게 재시작하고, 사용자가 스마트폰을 **2.4GHz Wi-Fi**로 바꿔 다시 시도하자:
  - 사용자: "아 이거 중간에 와이파이 2.4로 바꿧는데 껏다 켜야 되는거구나?" / "등록완료"
  - 시리얼 확인(`실측`): **`commissioned=yes`!**
  - 보너스 발견(`실측`): 커미셔닝이 끝나자 Matter 스택이 BLE 메모리를 자동으로 회수해 **`heap_free`가 `97KB → 169KB`로 72KB나 늘어났다.**

### 6.2 역사적 실측: SmartThings 앱 표시 항목과 루틴 조건

앱 화면을 연 사용자가 보고했다:
- 사용자: "1. 온도, 상태, 온도조절모드(꺼짐,난방), 난방온도 설정 만 있어. 2. 했어."
- 앱에서 모드를 `난방`, 목표온도를 `24°C`로 바꾸자 보드 시리얼에 즉시 찍혔다(`실측`):
  ```text
  [01_matter] app changed mode -> Heat
  [01_matter] app changed setpoint -> 22.50 C
  [01_matter] app changed setpoint -> 24.00 C
  ```
- 반대로 보드 시리얼에서 `t 19.5`, `s 23.0`, `h 1`을 보내자 앱의 `온도`가 `19.5°C`, `난방온도 설정`이 `23°C`, **`상태`가 `난방`**으로 바뀌었다!
- 그리고 대망의 루틴 조건 확인:
  - 사용자: **"1. 응 맞어, 상태도 난방으로 나와. 2. 상태 있어.70분 설정도 가능해."** (`실측`!!)

| 항목 | 앱 표시 (`실측`) | 양방향 동기화 (`실측`) | 비고 |
|---|---|---|---|
| 현재 온도 (`LocalTemperature`) | `온도` | 보드 → 앱 (`19.5°C`) OK | |
| 작동 상태 (`ThermostatRunningState`) | `상태` (`난방` / 대기) | 보드 `h 1` → 앱 `난방` OK | **루틴 조건 O, 70분 유지 O** |
| 운전 모드 (`SystemMode`) | `온도조절모드` (`꺼짐`, `난방`) | 앱 → 보드 OK | |
| 목표 온도 (`OccupiedHeatingSetpoint`) | `난방온도 설정` | 앱 ↔ 보드 양방향 OK | |

- **설계 확정:** 가장 큰 위험이었던 `ThermostatRunningState`와 70분 유지 루틴 조건이 **순정 Thermostat 엔드포인트 1개만으로 전부 동작**함을 실측으로 증명했다. 예비로 넣어 뒀던 보조 접점 센서(`MatterContactSensor`) 대체안은 통합 펌웨어에서 끄기로 했다.
- 마지막 남은 **유지 신호 최소 대기 펄스 길이(`p <sec>`) 실측**은 시간이 늦어 사용자 요청대로 후속 티켓 **`SCRUM-254`**로 분리 등록하고 `SCRUM-233`을 완료했다.

> 감탄 노트 후보: "상태 있어. 70분 설정도 가능해." — 어제 설계 문서에서 "안 되면 보조 센서 꼼수로 우회하자"고 적어 뒀던 최대 리스크가 순정 Matter 표준 그대로 한 번에 뚫린 순간.

> 웹 개발자 시선: 5GHz 폰으로 2.4GHz IoT 기기를 등록하려다 실패하는 건, 사내 VPN을 켠 채 로컬 `192.168.x.x` 장비에 붙으려다 타임아웃 나는 것과 같은 단골 삽질이다.

## 7. "근데 화면이 까맣게 나와" — 펌웨어 통합과 임베디드 지뢰 3개 (`SCRUM-242`)

Matter 등록까지 마친 뒤 보드를 본 사용자가 말했다.

- 사용자: "근데 화면이 까맣게 나와"
  - 당연했다. 지금 올라간 건 화면 드라이버가 없는 Matter 전용 데모(`demos/01_matter`)였다.
- 사용자: **"아 그럼 펌웨어 통합까지 하자 워크플로 돌려줘"**
- 확인해 보니 그사이 다른 세션에서 홈서버 센서 API(`SCRUM-239`, `GET /api/thermostat/sensors`, 테스트 62개 추가)도 머지 완료되어 **`SCRUM-242`의 선행 일감 6건이 전부 열려 있었다.**

단순히 모듈을 합치면 끝날 줄 알았지만, **합치는 순간에만 터지는 임베디드 지뢰 3개**가 기다리고 있었다.

### 7.1 지뢰 ①: ESP-IDF 5.5 I2C 신·구 드라이버 부팅 패닉 (설계 단계 사전 차단)

- 코드를 합치기 전 헤더를 확인하다 치명적인 충돌을 미리 발견했다(`문헌 기반`, SDK 소스 확인):
  - `ESP32_Display_Panel 1.0.0`(터치 GT911 + IO 확장 CH422G)은 ESP-IDF **구형** I2C 드라이버(`<driver/i2c.h>`, `i2c_driver_install`)를 쓴다.
  - Arduino ESP32 `3.3.12`(ESP-IDF 5.5 기반)의 `<Wire.h>`는 **신형** I2C 드라이버(`<driver/i2c_master.h>`, `i2c_new_master_bus`)를 쓴다.
  - ESP-IDF 5.5는 **한 바이너리에 신·구 I2C 드라이버가 동시에 링크되기만 해도 `setup()` 진입 전에 `CONFLICT! driver_ng is not allowed to be used with the legacy driver`로 `abort()` 패닉**을 일으킨다!
- `02_io`(Wire만 씀)와 `03_ui`(Display Panel만 씀)를 따로 돌릴 때는 몰랐다가, **통합할 때 비로소 터지는 전형적인 통합 버그**였다.
- **해결:** `Sht40Driver`와 `ClockRtc`, `02_io`에서 `<Wire.h>`를 완전히 걷어내고 `<driver/i2c.h>`로 통일했다. 통합 펌웨어에서는 `g_board.begin()`이 이미 열어 둔 `I2C_NUM_0`(SDA=8, SCL=9)을 SHT40과 RTC가 그대로 공유한다.

### 7.2 지뢰 ②: 3개 FreeRTOS 태스크 교차 락(데드락) 방지

- 통합 펌웨어에서는 3개의 FreeRTOS 태스크가 동시에 돈다:
  1. **CHIP 태스크** (Matter 앱 콜백 실행)
  2. **LVGL 태스크** (LVGL 뮤텍스를 잡은 채 터치 콜백 실행)
  3. **Arduino `loopTask`** (제어·센서·NVS·HTTP 실행)
- 만약 Matter 콜백 안에서 LVGL 뮤텍스를 잡거나, 터치 콜백 안에서 Matter API를 부르면 교차 락(데드락)이 걸릴 수 있다.
- **해결:** 두 콜백은 `portMUX_TYPE` 스핀락으로 보호된 `PendingMatterEvents` / `PendingUiEvents` 구조체에 값만 적고 즉시 반환한다. 오직 `loop()` 단일 태스크만 이벤트를 꺼내 순수 C++17 조정자 **`src/app/thermostat_app.*`**에 넘기고, 반환된 `SyncActions`를 NVS·Matter·UI에 반영한다.
- 이 구조 덕분에 양방향 동기화(에코 루프 차단, 앱 `Heat` 시 반복 모드 보존, 유지 신호 시 UI `난방 중` 유지 vs Matter `대기` 발행, 원격 센서 3회 실패 자동 전환)를 PC 호스트 단위 테스트(`test/test_thermostat_app.cpp` 10/10, 전체 7개 스위트 **93/93 PASS**, `실측`)로 미리 검증할 수 있었다.

### 7.3 지뢰 ③: 1시간짜리 첫 컴파일의 두 범인 (실전 트러블슈팅)

주니어(DeepSeek)가 통합 펌웨어 구현과 커밋 3건, 호스트 테스트 93/93을 25분 만에 끝냈는데, 마지막 `firmware/thermostat_main` ESP32 컴파일이 45분을 넘겨도 끝나지 않았다.

- 사용자: "왜이렇게 오래걸려? 좀 있으면 1시간이야." / "다시 도는건 아니지?" / "이건 또 왜이렇게 오래걸려" / "어휴.."
- `.build` 폴더의 중간 산출물(`.o`, `.libsdetect.d`)과 `cc1plus` 프로세스를 직접 뜯어보니 **정확히 두 가지 병목**이 겹쳐 있었다(`실측`):
  1. **범인 ① — LVGL 예제·데모 500개 파일 폭발:** Waveshare 오프라인 번들의 `lv_conf.h`에 `LV_BUILD_EXAMPLES 1`과 데모 5종(`WIDGETS`, `BENCHMARK`, `STRESS`, `MUSIC`, `KEYPAD`)이 전부 켜져 있었고, `lvgl/src/examples`·`lvgl/src/demos`에 안 쓰는 C 파일 ~500개가 들어 있었다. `03_ui` 혼자 빌드할 때는 `-I` 경로가 20개뿐이라 금방 끝났지만, `Matter`와 합치자 300개 `-I` 경로 × 700개 파일 전처리로 시간이 폭발했다.
     - **조치:** 전역 `Documents\Arduino\libraries`는 건드리지 않고, 프로젝트 격리 `AppData\Local\thermostat-esp32\sketchbook`에만 `examples`/`demos`를 뺀 경량 `lvgl`(C 파일 ~700개 → **192개**)을 구성했다.
  2. **범인 ② — `#include <Matter.h>` 한 줄의 위치:** `thermostat_main.ino` 맨 위에 `#include <Matter.h>`가 있었다. Arduino CLI의 라이브러리 탐지는 파일을 위에서 아래로 훑다 못 찾은 헤더를 1개 만날 때마다 **파일 맨 위부터 `g++ -E`를 처음부터 다시 돌린다.** 그 결과 아래쪽 라이브러리 15개를 하나씩 찾을 때마다 **40초짜리 `<Matter.h>` 전처리를 15번(10분 이상) 반복**하고 있었다!
     - **조치:** `#include <Matter.h>`와 `#include "thermostat_matter.h"`를 `#include` 목록 맨 끝으로 2줄 이동. 11분 동안 0개였던 탐지가 수정 직후 5분 만에 뚫리고 분당 20~25개 속도로 빠르게 진행되기 시작했다(`실측`).

> 책 소재: **"`#include` 두 줄의 순서가 빌드 시간을 10분 줄인다."** 웹 번들러(Vite, esbuild)에 익숙한 개발자에게 C/C++ 전처리기와 Arduino CLI의 라이브러리 탐색 방식이 얼마나 무식하고 정직하게 동작하는지 보여 주는 최고의 트러블슈팅 에피소드다.

> 웹 개발자 시선:
> - I2C 신·구 드라이버 충돌 = 하나의 앱에 호환 안 되는 React 17과 React 18 런타임이 동시에 번들되어 부팅 크래시 나는 상황.
> - `portMUX_TYPE` pending 이벤트 + `loop()` 단일 소비자 = Redux/Flux 단방향 데이터 흐름. 여러 곳에서 상태를 직접 고치지 않고 액션(이벤트)만 던져 메인 루프가 한 번에 처리한다.
> - LVGL `examples`/`demos` 제외 = `node_modules`에서 테스트·스토리북 파일까지 전부 Babel/TypeScript로 트랜스파일하고 있던 `tsconfig` `exclude` 누락을 고친 것.

> 교훈: 따로 떼어 놓고 잘 도는 모듈을 합칠 때 비로소 나타나는 버그가 있다(드라이버 버전 충돌, 스레드 교차 락, 전처리 시간 곱셈 폭발). 통합은 단순 복붙이 아니라 별도의 설계 단계다.
